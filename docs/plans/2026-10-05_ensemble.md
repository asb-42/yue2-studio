# Ensemble (SATB quartet) support — problem, analysis, options

Status: analysis + prototype plan, not started.
Date: 2026-10-05.

## 1. Problem statement

YuE2 Studio generates songs with one or two vocal lines well, but not an
ensemble of four distinct voice groups (quartet, e.g. SATB: soprano / alto /
tenor / bass). A style prompt such as "barbershop quartet, four male harmony
voices" (`app/examples/demo-7c4199efbd27b2494e10d289.json:3`) produces at best
a blended choir effect in a single vocal track — not four separable,
individually editable voice parts with correct voice leading, section
alignment, and mix control.

Goal of this plan: record where the limit lives, what can be fixed in code,
what is blocked by the model/engine, and how a production workflow
(orchestrator: 4 solo runs + mixdown) can deliver quartets without retraining.

## 2. Detailed analysis

### 2.1 Score dialect is hardwired to two voices

- `crates/music-server/src/score/mod.rs:1`, `score/abc.rs:1`: "limited
  two-voice ABC dialect".
- `score/abc.rs:12`: `VOICES = ["Vocal", "Ins"]`; `abc.rs:23` exact
  `VOICE_LINES` header required.
- `score/abc.rs:292,310,325-327,359,366`: `parse()` refuses anything else —
  each group must be a `V: Vocal` block followed by a `V: Ins` block with
  equal measure counts (1–4 bars after `Z` expansion).
- `score/abc.rs:371`: chord symbols belong in `Vocal`, never in `Ins`.
- `assistant.rs:52` (`SCORE_CONTRACT`): "Both voices are single melody lines;
  Ins is an instrumental theme or solo, never a chord staff."
- `Score.voices: [Voice; 2]` (`abc.rs:180`) ripples through `notation.rs`,
  `rebuild.rs`, `phrasing.rs`, `transpose.rs`, `export/smf.rs`,
  `import/parts.rs`, and `app/components/ScoreView.tsx:12` (two staves).

There is no SATB / 4x `V:` representation. This is deliberate, mirroring the
model's planning stage, not an oversight.

### 2.2 Lyrics / style prompts cap at duet, forbid singer tags

- `assistant.rs:48` (`DUET_RULE`): "YuE2 has no singer tags, so do not write
  singer cues into the lyrics; let the sections themselves — a verse each, a
  shared chorus — carry the exchange."
- `assistant.rs:29-37` (`LYRICS_RULES`): no stage directions, singer cues,
  instruments, or pronunciation marks; tags limited to `[Intro]`, `[Verse 1]`,
  `[Pre-Chorus]`, `[Chorus]`, `[Bridge]`, `[Instrumental Break]`, `[Outro]`.
- `assistant.rs:203-210` (`wants_two_voices()`): triggers only on
  `duet / two voices / male and female / ...` cues. No `quartet / SATB /
  four voices` cue exists.
- `assistant.rs:940-949`: test asserts `[Male Vocals]`-style tags never
  appear.

Prompting four distinct groups is therefore actively stripped by the
assistant contract.

### 2.3 MIDI import collapses to two monophonic lines

- `score/import/mod.rs:13-21`: "The two lines are the parts `parts::choose`
  picks, each one note at a time"; simultaneous notes keep the top one; a
  lower note under a higher one is dropped unless mostly disjoint.
- `import/mod.rs:111` (`Notice::Struck`): "A line of the score holds one note
  at a time, so the top note of each chord was kept."

A 4-part MIDI (SATB on 4 tracks) cannot survive the import.

### 2.4 Engine request has no voice count / multi-track conditioning

- `lib.rs:211` (`CreateMusicJobRequest`): `{ style, lyrics, abc, cot, ... }`.
  No `voices / tracks / parts` field.
- `lib.rs:7826` (`yue_request_from()`): forwards `style / lyrics / abc / cot /
  seeds / duration / transpose / adapters` to `yue-server`. Per-part
  conditioning is protocol-absent.
- `crates/music-engine/src/yue_server.rs`: supervisor only launches and
  health-checks the external `yue-server` binary (pinned
  `engines/yue2-cpp-source.json`, commit `1141479`); it does not interpret
  ABC. What 3rd/4th voices mean is decided by `yue2.cpp` + YuE2 weights.

### 2.5 Downstream assumes one mixed vocal

- `separation.rs:120`: HT-Demucs 6-stem `STEMS` returns a single `vocals`
  stem. Four rendered voices would come back mixed, not separated.
- Karaoke / Parakeet alignment (`lyrics_sync.rs`, `prepare.rs` vocal stages):
  one timeline, one transcript per song; one `vocals.wav` per dataset item
  (`training.rs:582-592`).
- `audio-post/` offers `denoise / lifter / naturalize / mastering / limiter`
  but no multitrack mixdown (no per-track alignment, gain, pan, glue reverb).

## 3. Blockers

### 3.1 Fixable in studio code (large but bounded)

Parser Nat `Vec<Voice>`, import `parts::choose`, assistant prompts
(quartet cues + singer-tag policy), `ScoreView`/MIDI editor staves,
`phrasing`/`transpose`/`rebuild`/`export`, `wants_two_voices` →
`wants_n_voices`. Estimated touch: most of `score/*`, parts of
`assistant.rs`, `lib.rs` validation, UI components. No new dependency class.

### 3.2 Not fixable in studio code (hard blockers)

- **YuE2 checkpoint + `yue-server`**: trained on solo/duet + accompaniment
  planning (`Vocal` + `Ins`). A 3rd/4th `V:` line is out-of-distribution:
  expect ignore / blend / garbage. Changing this needs retraining, a new
  checkpoint, or a different multi-voice model — outside this repo.
- **SheetSage2 transcriber, HOT-Step trainer**: same two-voice assumption
  (scores stage, one `vocals.wav` per item, `yue_train.rs:467`).
- **Source separation**: no per-voice stems from a mixed render without
  separate renders.

Conclusion: native 4-voice single-pass generation is **not** a studio-code
task. The studio can only orchestrate around the model.

## 4. Solution options

| Option | What | Pros | Cons |
|---|---|---|---|
| A. Native multi-voice model | Retrain/fine-tune or swap checkpoint; extend protocol + parser | True SATB, one pass, locked harmony | Out of scope: training cost, no weights, protocol + all downstream changes |
| **B. Orchestrator (recommended)** | SATB score → 4 native 2-voice ABCs → 4 sequential YuE2 solo runs + 1 instrumental → mixdown | Fits today's model; each run valid input; no retraining; shippable as workflow | No cross-part conditioning: intonation/timing/timbre drift; mixing needed; 4–5x GPU time |
| C. Choir-effect LoRA | Style/adapter only (e.g. `bulgarian-voices`, `qwwl` in `adapter-catalog.json`) | Zero code | Blended choir, not 4 distinct editable parts |
| D. External DAW only | Studio renders stems, user mixes elsewhere | Zero code | No guidance, no reproducibility, manual alignment |

## 5. Implementation approach (option B, orchestrator)

No native multi-track extension of the model. Instead a production workflow:

```text
SATB partitur (4 monophonic lines, shared bars/sections/tempo/duration/text)
  ├─ Part 1 Soprano → YuE2 run 1 (Vocal=S, Ins=shared/muted)
  ├─ Part 2 Alto    → YuE2 run 2 (Vocal=A, Ins=shared/muted)
  ├─ Part 3 Tenor   → YuE2 run 3 (Vocal=T, Ins=shared/muted)
  ├─ Part 4 Bass    → YuE2 run 4 (Vocal=B, Ins=shared/muted)
  └─ Instrumental   → YuE2 run 5 (instrumental flag / Instrumental LoRA)
           ↓
4 vocal recordings (+ `vocals_only` extraction) + 1 accompaniment track
           ↓
time-align → gain/pan → glue reverb → master (external DAW first, in-studio mixdown later)
```

Per-part requirements (enforced by the splitter, pre-composed by user or
writing assistant — the model does not invent voice leading):

- identical bar structure, `M:/L:/Q:/K:`, `%`-section boundaries;
- identical duration/tempo (`duration_seconds`, `cot`, BPM in style);
- same text distribution strategy per part (unison vs. divisi explicitly
  notated, syllable counts matched to each line's note counts);
- functionally coherent voice leading (close position, no parallel fifths/
  octaves unless intended, singable ranges per part);
- shared style skeleton (genre, production, BPM); only the vocal descriptor
  differs per part (e.g. "airy soprano" vs. "deep bass").

Known residual limits the orchestrator does **not** remove (must be
documented, not hidden): no singer-ID (timbre drifts between runs), no
shared phoneme clock (each run times phonemes autonomously), octave
displacement by the model (bass sung up an octave), pronunciation drift
across runs, 4–5x render cost.
